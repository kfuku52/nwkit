# NWKIT リポジトリ調査と改善案

**修正追記:** 以下は修正前の調査記録である。確認した5件は0.43.25で修正した。

## 結論

優先すべき問題は、**入力ファイルの破損防止と、最適化結果の収束表示の正確さ**である。
静的検査や多数の回帰テストは整備されているが、共通機能を各コマンドへ適用する際の抜けが残っている。
以下の5項目は実行によって再現した。数値例は合成目的関数であり、実データの推定結果全般が誤っていると結論するものではない。

| 優先度 | 確認した問題 | 主な影響 | 改善の要点 |
| --- | --- | --- | --- |
| P1 | shift-simulate の監査対象が不足 | 入力・真値JSONの破損、ハッシュ記録漏れ | 入出力登録と監査先衝突検査を統一 |
| P1 | annotate のレポートが入力TSVを上書き可能 | 元データの消失 | 出力同士だけでなく入力との衝突を検査 |
| P2 | スカラー最適化の探索順と成功判定 | より悪い解を収束成功として返す | 最良候補の領域を必ず精密化し、その候補の収束を評価 |
| P2 | 単独Newick出力が直接書き込み | 書き込み障害で既存結果が部分ファイルになる | 既存のトランザクション処理を適用 |
| P2 | rename が重複TSVヘッダーを受理 | 意図しない名前への置換 | ヘッダーの一意性と行幅を検証 |

## 1. shift-simulate の監査対象不足 — P1

根拠: [provenance.py](../../nwkit/provenance.py) の `INPUT_PATH_ARGUMENTS`（72行付近）、
`OUTPUT_ARGUMENTS`（26行付近）、`_audit_collision_candidates`（851行付近）、
`run_with_audit`。コマンド本体の入力保護は [shift_simulation_cli.py](../../nwkit/shift_simulation_cli.py) 246行付近。

`parameters` と `model_in` が入力一覧になく、`truth_out` と `latent_out` が出力一覧にない。
通常の監査でも、今回の再現例では `inputs` が `infile` のみ、`outputs` が `outfile` のみになる。
生成モデルと真値ファイルのハッシュが残らない。

さらに `--audit` に `--parameters` と同じパス、または `--truth-out` と同じパスを渡しても拒否されない。
処理後、監査レコードがそのJSONへ追記され、`json.loads` が `Extra data` で失敗する。
これは監査ログの欠落だけでなく、解析入力・出力を実際に壊す問題である。
`model_in` / `latent_out` の登録漏れはコードで確認したが、それらを使う実行シナリオは今回個別には再現していない。

改善案:

- まず4オプションを正しい役割の一覧に登録し、通常監査でのハッシュ記録と衝突拒否を回帰テストにする。
- 衝突検査は監査ファイルの作成・権限変更より前に実行する。
- 長期的にはCLIの入出力メタデータを単一の定義にまとめ、監査・標準入力管理・入力保護が同じ定義を参照する。
- パス同一、相対パス別名、シンボリックリンク、ハードリンクのケースを検証し、拒否後に元ファイルの内容が不変であることも確認する。

## 2. annotate のレポートによる入力破壊 — P1

根拠: [annotate.py](../../nwkit/annotate.py) 461–469行。

`validate_distinct_output_paths` は `--outfile` と `--report` の衝突しか確認しない。
`--table traits.tsv --report traits.tsv` を指定すると、処理は成功し、入力の形質表が注釈レポートに置き換わる。
出力トランザクションがあっても、書き込み先の役割自体が誤っていれば防げない。

改善案:

- 既存の `validate_outputs_do_not_replace_inputs` を使い、少なくとも `--table` と補助出力の衝突を事前拒否する。
- 同じ検査を他の複数入力・補助出力コマンドにも横断的に適用する。
- 主Newickの意図的な同一ファイル更新を許すかは互換性上の方針として分けて扱う。補助レポートが入力表を壊す現象とは区別する。

## 3. スカラー最適化の精密化順と収束判定 — P2

根拠: [optimization.py](../../nwkit/optimization.py) 100–143行。

`local_indices` は座標順で作られ、`local_indices + ranked_indices` の先頭4候補だけを精密化する。
このため局所最小が5個以上あると、グリッド上で最良の候補さえ精密化されない場合がある。
また返却する `success` は選択した候補自身ではなく、「どこかの局所探索が成功したか」で決まる。

再現した目的関数は `min_i(100 * (x - center_i)^2 + offset_i)`、区間 `[0,16]`、
中心 `[1,3,5,7,9.25]`、オフセット `[0,0,0,0,-10]`。
結果は `x=9.0, fun=-3.75, success=True` だが、既知の最良解は `x=9.25, fun=-10`。
粗いグリッドの限界だけではなく、最良グリッド点を既に発見しているのにその領域を精密化しない。

呼び出し元には通常回帰、PCA、連続形質ASR、native shift がある。
今回、各生物学的モデルで同じ失敗が発生することまでは確認していない。

改善案:

- 最良グリッド点を必ず精密化対象に含め、局所最小候補を目的関数値で優先する。
- `success` は採用された候補の収束状態を表すようにし、探索全体での成功数は別フィールドに残す。
- 5つ以上の極小、失敗した精密化、境界解、有限点が疎な関数について回帰テストを追加する。
- 予算付きの探索であることを明記し、数学的な大域最適保証と混同させない。

## 4. 単独Newick出力の障害耐性 — P2

根拠: [util.py](../../nwkit/util.py) 1440–1445行、
[tree_outputs.py](../../nwkit/tree_outputs.py) 25行以降。

`write_tree` のファイル出力は `open(..., 'w')` で既存ファイルを切り詰めてから書く。
シリアライズは先に済ませているが、書き込み自体の途中失敗には対応しない。
5文字書いた直後に `OSError` を発生させた再現例では、既存内容 `ORIGINAL` が `(A:1,` に変わって残った。
これは障害注入で確認した経路であり、実際のディスク障害を発生させたわけではない。
`write_tree_with_tables` も補助表がない場合はこの経路を使う。

改善案:

- 通常のパス出力を既存の `output_transaction` に統一する。
- 標準出力・ファイルオブジェクト・既にステージ済みの書き込みは別経路のまま維持し、二重ロックを避ける。
- 途中のI/O例外、既存ファイルの権限、シンボリックリンクの既存仕様、同一入力出力の扱いを検証する。
- トランザクションの既存説明どおり、複数ファイルのプロセスクラッシュ時の完全な原子性までは約束しない。

## 5. rename の重複ヘッダー受理 — P2

根拠: [rename.py](../../nwkit/rename.py) 15–41行。

次の入力を `read_name_tsv` に渡すと、エラーにならず `{'A': 'C'}` を返す。

```text
old_name<TAB>new_name<TAB>new_name
A<TAB>B<TAB>C
```

`csv.DictReader` が同名の列を後勝ちで格納するため、Bという情報が黙って捨てられる。
別のTSV読込処理（例: `table2nwk._validate_column_headers`）には重複拒否があり、コマンド間で契約が揃っていない。

改善案: ヘッダーの重複・空名とレコードの列数不一致を検査し、既存の文字列保持方針を維持する。
重複キー行、重複列、欠けたセル、余分なセルを区別してテストする。

## テスト失敗の切り分け

`python tools/check.py quick` は **4038 passed, 4 failed, 86 skipped, 12 deselected**。
別途 `python tools/check.py test -- -m slow` は **12 passed**。
合計で収集された4140件すべてが両選択のどちらかに含まれ、4050成功・4失敗・86スキップだった。
スキップされたケースの実動作を検証したことにはならない。

4失敗の内訳:

1. `test_native_optimization_audit.py::test_screen_harness_rejects_invalid_sizes_and_colliding_outputs` の3ケース。
   利用した代替PythonにはNWKITがインストールされておらず、別プロセスのスクリプトが `ModuleNotFoundError` になった。
   `PYTHONPATH="$PWD"` を与えた絞り込み再実行では3件成功した。
   READMEのeditable installを済ませた正式な開発環境と同一条件ではないため、製品バグとして数えない。
2. `test_discrete_asr_models.py::test_mk_multistart_handles_penalty_regions_on_long_branches`。
   単独再実行でも失敗。尤度は `-3.6669384880343445` でテスト期待値の許容範囲内、24開始点すべて収束。
   推定レートの一つが `1e-9`（実際の下限）になり、実装は `rate_lower_boundary` を正しく出したが、テストは `ok` を要求する。
   現環境で尤度推定が壊れている証拠ではない。ほぼ同じ尤度を持つ境界付近の解に対し、テスト期待値の根拠を見直す必要がある。
   許容誤差を無条件に緩めるのではなく、独立の尤度評価・境界診断との整合性を確認してテスト契約を修正する。

絞り込み再実行: **3 passed, 1 failed**。この結果を全件再実行の成功としては扱わない。

## 保守性の改善候補

これらは再現済みの不具合とは別の、中期的な設計改善案である。

- **入出力定義の統一**: 監査、標準入力、出力保護の手動登録を減らす。今回の最も直接的な根本対策。
- **巨大モジュールの責務分割**: `cli.py` 6594行、`regress.py` 4904行、`image.py` 4621行、`asr.py` 4349行。
  行数自体を不具合とせず、入出力検証・モデル指定・結果レコードなど明確な境界から段階的に分離する。
- **型検査の実効性**: ASTで数えた関数3116個のうち返り値注釈があるものは249個。
  注釈率は品質の直接指標ではないが、mypy成功だけでモデル間の辞書キーや結果構造の整合性が保証されるわけではない。
  公開結果とコマンド境界から `dataclass` / `TypedDict` を導入する。
- **横断的な契約テスト**: 全コマンドの正常系到達テストは既にある。そこへ入力・補助出力の衝突、重複ヘッダー、書込失敗を追加する。
  単にテスト数やカバレッジ値を増やすより、今回漏れた性質を検証する。
- **開発環境の再構築**: 既存 `.venv/bin/python` は別アーキテクチャのPythonを参照し、`bad CPU type` で起動できなかった。
  既存環境を勝手に削除せず、ホストと合うPythonで新しい環境を作り、文書どおりの制約付きeditable installで再検証する。

## 推奨する実施順と完了条件

1. 監査・annotateの入力保護。全衝突ケースを変更前に拒否し、入力ハッシュが不変であること。
2. 単独出力のトランザクション化。障害注入後も既存結果が保持されること。
3. 最適化の候補選択・収束情報。合成多峰関数と既存の数値参照テストの両方を通すこと。
4. TSV契約統一。誤った表は明確に拒否し、正常表・文字列識別子・既存CLIとの互換性を保つこと。
5. 正式な開発環境で境界解テストを精査し、`full` / `dist` と対応Python・OSのCIを実行すること。
