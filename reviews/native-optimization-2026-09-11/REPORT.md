# Native SHIFT: 木構造の再利用と候補行列の省メモリ化 — 2026-09-11

共分散推定込みの単発探索で、今回の3条件の実行時間中央値が **30.5〜41.2%短縮**した。候補数・探索予算を減らす変更ではなく、すべての比較で候補記録、尤度、選択配置、探索メタデータが完全一致した。

実装・検証が完了したのは、既存の推定法を保つ最適化の段階である。EM型の新しい探索、active set、統計的な本番採用まで完了したという報告ではない。

推定条件は形質ごとにαと過程分散を推定する。測定誤差の追加分散は推定していない。固定条件はα=0.3、過程分散=1。探索測定の入力は完全観測で、既知測定誤差なし。報告する配置は無罰則尤度によるもので、ICや校正後の検出精度の評価ではない。

3回すべての記録を照合した。[生データと照合結果](final-measurements/equivalence.json)に各回の時間・RSSがある。小差の1,000葉固定条件を含め、時間短縮率を別の入力に外挿することはできない。RSSには実行間の変動があり、表はメモリ上限の保証ではない。

## 候補行列生成の測定

1,000葉・4形質、形質ごとに約9%の欠測と既知観測分散0.04。固定共分散で標準化した枝列と、標準化しないOU optimum-increment列を比較した。

各条件・各版を3つの新規プロセスで実行し、各プロセスでウォームアップ1回と計測3回を実施した。表の時間はプロセス内中央値の中央値、RSSはプロセスごとのピークの中央値である。

| 条件 | 実時間・秒（旧→新） | 時間変化 | ピークRSS中央値・MiB（旧→新） |
|---|---:|---:|---:|
| 均衡木・標準化した枝列 | 0.132 → 0.115 | -13.1% | 416.1 → 357.4 |
| 均衡木・optimum increment | 0.168 → 0.182 | +8.2% | 450.7 → 354.8 |
| 櫛状木・標準化した枝列 | 0.127 → 0.116 | -8.4% | 255.8 → 259.0 |
| 櫛状木・optimum increment | 0.182 → 0.159 | -12.5% | 295.7 → 276.5 |

全行列・応答・枝順序を `rtol=1e-12, atol=1e-12` で照合し、観測した最大絶対差は **0** だった。大きなNPZは比較用の一時ファイルとして作成・比較後に削除し、再生成用ハーネスと照合結果を保持している。

**すべての小処理が速くなったわけではない。** 均衡木のoptimum-increment生成はこの測定で約8%遅く、RSS中央値は約21%減った。一方、櫛状木の標準化列ではRSSがわずかに増えた。メモリと時間の両方が常に改善するという主張はしない。各回のRSSのばらつきは生データで確認できる。

## 実装と根拠

変更前の128葉・2形質・共分散推定込み探索をプロファイルすると、探索10.768秒中、モデル再推定が10.324秒、白色化因子の構築が6.807秒だった。これは計装下での診断であり、上表の無計装の時間とは比較しない。[プロファイル](profile-before.txt)

PhylogeneticEMはE-stepのモーメント計算に木の上下走査を用いる。[公式ドキュメント](https://pbastide.github.io/PhylogeneticEM/reference/PhyloEM.html)を参考に、今回はすでに存在する木上の白色化について、繰り返し構築していた構造を再利用する設計を優先した。

- `gaussian_whitening.py`: 子・親・走査順序・順序付き観測tip番号をキーとして、白色化の構造のみを最大16件キャッシュする。分岐長、α、分散、trait値をキャッシュのキーや値に取り込まない。回転・スケール・行列式は毎回新しく計算する。トポロジー配列は読み取り専用。
- `shift_native_screen.py`: 枝の子孫tip区間から必要な列を生成する。白色化を512〜4,096列のブロックで実行し、深い木では走査コストを分散するため幅を広げる。最初のブロックと切片・応答を同じ走査で処理する。非情報的な列の閾値はブロック単位に変更せず、全列のノルムから計算する。
- `shift_native_quick.py`: 全枝の行列を作ってから候補だけ取り出す処理を、最初から候補枝だけを作る処理に変更する。

最終的なscreening行列は依然として密行列であり、matrix-free化ではない。従来の保守的なメモリ予算の受付判定を保持している。この予算はプロセス全体のピークRSSを制限しない。

固定512列の初期案では、櫛状木の標準化列生成が約0.129秒から0.251秒へ遅くなった。この案は採用しなかった。[初期案の測定](measurements/equivalence.json)は最終版と区別して残している。深さに応じた幅と最初の走査の共有を追加し、最終版で再検証した。

## 再現

Apple M2 Max上のx86_64 Python 3.10.14、NumPy 1.26.4、SciPy 1.15.2。OpenBLAS/MKL/OMP/VECLIBを1スレッドに固定した。[NumPyビルド情報](numpy-build.txt)と[manifest](final-measurements/manifest.json)に環境、全ソースhash、実行コマンドを記録した。自分のテストと性能測定は並走させていないが、共有ホストを完全に専有した測定ではない。

比較対象は作業ツリーの凍結コピーであり、コミット同士の比較ではない。[changes.patch](changes.patch)は新旧3ファイルの差分で、最終版の別コピーへ `git apply --unidiff-zero --reverse` で逆適用すれば比較元を復元できる。元の作業ツリーで逆適用しないこと。

```sh
python reviews/native-optimization-2026-09-11/run_benchmarks.py \
  --before /path/to/before-source --after /path/to/after-source \
  --output /tmp/native-optimization-new
```

ハーネスは同じ `tools/benchmark_native_search.py` と `tools/benchmark_native_screen.py` を両ソースに対して使う。出力ディレクトリは新規でなければならない。通常は探索も新旧を交互に3回実行する。

今回の最終探索比較では、変更していない旧版の3回の測定を `--before-results` で再利用し、最終新版を3回再測定した。再利用時には旧版の全ソースhashの一致を検証した。従って最終探索表の新旧は完全な交互実行ではない。最終候補行列測定は新旧を交互に3プロセスずつ実行し直した。すべて同じ環境・入力・スレッド設定で実施している。
